## Project Problem

The Capacitated Vehicle Routing Problem (CVRP) asks how to route vehicles from a central depot to a set of customers while meeting customer demand and obeying vehicle capacity limits. Each customer must be visited, each vehicle starts and ends at the depot, and the project goal is to compare algorithms based on total route distance, runtime, and number of routes used.

Our project is titled **Capacitated Vehicle Routing Problem Algorithm Comparison**. The final version of the project will compare three approaches: the Nearest Neighbor Heuristic, the Clarke-Wright Savings Algorithm, and Harmony Search. These algorithms were chosen because they represent different styles of algorithmic problem solving. Nearest Neighbor gives us a simple greedy baseline, Clarke-Wright Savings gives us a well-known CVRP construction heuristic, and Harmony Search gives us a metaheuristic method that can be compared against the more direct heuristic approaches.

## Completed So Far

The repository structure for the project has been created with folders for code, data, results, tables and graphs, and reports. This gives the project a clear organization for implementation, experiments, analysis outputs, and written deliverables.

The Nearest Neighbor baseline algorithm has been implemented. It starts at the depot, repeatedly selects the closest unvisited customer that fits within the remaining vehicle capacity, and starts a new vehicle route when no feasible customer remains.

A small sample dataset has been created in CSV format. Customer `0` is the depot, and the remaining customers have coordinates and demand values for testing the starter implementation.

The experiment runner loads the sample dataset, runs the Nearest Neighbor baseline with a vehicle capacity of `40`, records runtime, calculates total route distance, counts the number of vehicle routes, prints readable routes, and saves the results to `results/raw_results.csv`.

## Coding Progress

The main coding work completed for checkpoint 2 is the Nearest Neighbor CVRP baseline. The implementation includes a Euclidean distance function, route distance calculation, total distance calculation, and the main `nearest_neighbor_cvrp` function. The algorithm keeps track of unvisited customers and remaining vehicle capacity. It only adds a customer to a route if that customer's demand fits within the remaining capacity, so every route generated by the baseline respects the vehicle capacity limit.

The experiment runner is also complete for the current baseline. It loads customers from the CSV file, treats customer `0` as the depot, runs the algorithm, measures runtime in milliseconds, calculates total route distance, counts the number of routes, prints the routes in readable format, and writes the summary result to a CSV file. This gives us a repeatable process that can be reused when the other algorithms are added.

## Results Generated

The current sample experiment uses a vehicle capacity of `40` and serves `10` customers plus the depot. The Nearest Neighbor baseline generated `4` vehicle routes on the starter dataset. The recorded total route distance was `365.13`.

The routes produced during the test run were:

- Route 1: `0 -> 10 -> 7 -> 1 -> 0`, demand `40`
- Route 2: `0 -> 5 -> 8 -> 6 -> 0`, demand `40`
- Route 3: `0 -> 9 -> 4 -> 3 -> 0`, demand `40`
- Route 4: `0 -> 2 -> 0`, demand `15`

These results are saved in `results/raw_results.csv`. The CSV records the algorithm name, dataset name, number of customers, vehicle capacity, runtime, total route distance, and number of routes. This format will make it easier to compare algorithms later because every algorithm can write results using the same columns.

## Experimentation Decisions

For this checkpoint, we decided to begin with a small custom dataset instead of immediately using full CVRPLIB benchmark data. This makes it easier to test the code, check route capacity by hand, and verify that the experiment runner is saving the correct output. Customer `0` is used as the depot, which matches the convention used in many routing examples.

We also decided to use total distance, runtime, and number of routes as the main comparison metrics. Total distance measures solution quality, runtime measures algorithm efficiency, and number of routes shows how many vehicles are needed. These metrics are simple enough for the checkpoint but still meaningful for the final comparison.

The next dataset step is to prepare CVRPLIB instances and convert them into a format that the experiment runner can load. Once that is done, each algorithm can be tested on the same benchmark instances.

## Experience So Far

So far, the project has helped us turn the CVRP problem description into working code. One useful part of the process was separating the algorithm implementation from the experiment runner. This makes the code easier to extend because new algorithms can be added without rewriting the dataset loading and result recording process.

The Nearest Neighbor algorithm was a good starting point because it is easy to understand and gives us a baseline for later comparison. It also showed why CVRP is more complex than a basic shortest-path or nearest-city problem: the vehicle capacity constraint affects which customer can be selected next and when a new route must begin.
